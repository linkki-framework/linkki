===== Vaadin 25.3

Vaadin 25.3 introduced several changes that affect this release and may also affect downstream projects:

* *Frontend styling of `vaadin-form-item`* +
Vaadin reworked the internal styling of `vaadin-form-item`. Form items used in linkki layouts are not affected, as linkki's own styling was adjusted accordingly. Projects with custom CSS targeting `vaadin-form-item`'s required-indicator or label parts should check and adjust it if needed.
* [.api-change]*Deprecated icons* +
Several `VaadinIcon` entries are now deprecated (llink:https://github.com/vaadin/web-components/pull/12452[explanation from Vaadin]). +
This changed the default icon of two linkki annotations:
** `@BindIcon`: default changed from `VaadinIcon.NATIVE_BUTTON` to `VaadinIcon.SQUARE`
** `@UIMenuList`: default changed from `VaadinIcon.ELLIPSIS_DOTS_H` to `VaadinIcon.ELLIPSIS_H`
+
Projects that explicitly used `@BindIcon(VaadinIcon.SQUARE)` together with the default `iconType() == IconType.AUTO` need to set `iconType = IconType.STATIC` explicitly: `VaadinIcon.SQUARE` is now the sentinel value `@BindIcon` uses to detect "no icon set" (dynamic icon binding). See the `@BindIcon` javadoc. +
All usages of deprecated icons need to be investigated as the canoncial substitute does not always express the same intention as the existing one.
As Vaadin ist planning to migrate to link:https://lucide.dev/icons/[Lucide icons], it may be useful to consider if the corresponding Lucide icon still express the same meaning when choosing replacements.
* [.api-change]*`TreeGrid` data provider* +
`TreeDataProvider(TreeData)` is now deprecated in favor of `TreeDataProvider(TreeData, HierarchyFormat)`, because the single-argument constructor's default hierarchy format will change from `NESTED` to `FLATTENED` in Vaadin 26. linkki's `TreeGridComponentWrapper` was adjusted accordingly. Projects with their own `TreeGrid`/`TreeDataProvider` usage should switch to the two-argument constructor and pass `HierarchyFormat.NESTED` explicitly to keep the current behavior.
* *Vaadin TestBench dialog behavior* +
Vaadin TestBench 25.3 changed dialog-overlay DOM/timing behavior. This is mitigated internally in `OkCancelDialogElement.getDialogLayout()` and `VaadinElementConditions.isClosed(DialogElement)` (module `linkki-vaadin-flow-testbench-extension`). Projects with their own TestBench page objects or conditions for dialogs may be similarly affected and should verify against this Vaadin version. The most likely (but not confirmed) root cause is a combination of two Vaadin 25.3 web component changes: `vaadin-dialog`'s light DOM slot structure for its header/footer wrappers changed, and the shared overlay animation/attribute-timing logic was reworked, affecting all `vaadin-overlay`-based components including dialogs.
* *Node.js 24 and version-specific install directories* +
Vaadin 25.3 changed how it installs/manages Node.js: instead of a single `~/.vaadin/node/` directory, each version is now installed into `~/.vaadin/node-v<version>/`, and the `node.auto.update` configuration property was removed since it's no longer needed. Node.js 24+ is still required for building the frontend. Projects with their own Node.js provisioning/CI caching tied to the old layout or `node.auto.update` should adjust.
* *Incompatible Chromedriver Version* +
The Selenium version is updated to 4.49.0. This may cause various exceptions when executing testbench UI tests that should resolve with using a more recent Chromedriver version (tested with 149).

==== Components, UI Annotations and Aspects

// https://faktorzehn.atlassian.net/browse/LIN-4839
* *Dynamic severity for badges* +
The new annotation `@BindBadgeSeverity` allows the severity of a badge (`@UIBadge`) to be determined dynamically from the presentation model, instead of only statically via `@UIBadge#severity()`.
A method `get<PropertyName>BadgeSeverity()` returning a `BadgeSeverity` must be provided on the presentation model.

==== Other Improvements

// https://faktorzehn.atlassian.net/browse/LIN-4151
* [.api-change]*`linkki-bom` no longer imports the Vaadin BOM* +
Importing `linkki-bom` alone no longer pins the versions of Vaadin artifacts, since this could conflict with the Vaadin version managed by a consuming application's own parent POM. +
Projects that relied on `linkki-bom` to manage Vaadin versions transitively must now import `com.vaadin:vaadin-bom` themselves, or otherwise pin the Vaadin artifact versions they use directly.

==== Components, UI Annotations and Aspects

// https://jira.convista.com/browse/LIN-4626
* *UIOpenDialogButton mit ButtonVariant*
The annotation <<ui-open-dialog-button, `UIOpenDialogButton`>> now has an attribute `variants` to define the variants of the button.
// https://jira.convista.com/browse/LIN-4875
* *BindFormItemLabelWidth* +
The new aspect <<bind-form-item-label-width, `BindFormItemLabelWidth`>> allows changing the label width for all items within the annotated section.
// https://jira.convista.com/browse/LIN-4885
* *`UIMenuList` supports submenus* +
`MenuItemDefinition` now supports nested sub-items via `MenuItemDefinition.Builder#subItems(List)`.
A MenuItemDefinition with sub-items acts as a submenu parent instead of a leaf action item.
Submenus are rendered and updated recursively, with `enabled` and `visible` state propagated at all levels.
For more information see <<ui-menulist, UIMenuList>>.
// https://jira.convista.com/browse/JTS-3338
* *`@UIOpenDialogButton`: dialog can now be shown conditionally* +
The annotated method may now return `null` to indicate that no dialog should be opened under certain conditions.
In this case, the binding context is still updated.
